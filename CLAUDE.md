# Budget Ledger

Personal budget tracking app built with Next.js and Supabase.

## Commands

- `pnpm dev` - Start dev server
- `pnpm build` - Production build (use to verify changes compile)
- `pnpm start` - Start production server
- `pnpm test` - vitest (`lib/**/*.test.ts` and `test/**/*.test.ts`)

## Stack

- **Framework**: Next.js 16 with React 19, TypeScript
- **Database**: Supabase (PostgreSQL with RLS)
- **Package manager**: pnpm
- **Charts**: SVG, from `d3-scale`/`d3-shape`/`d3-array`/`d3-hierarchy` (submodules, not the full `d3` bundle)
- **Avatars**: `@dicebear/core` + `@dicebear/styles` (the `croodles-neutral` definition only, ~24KB of JSON)
- **Animation**: `motion` (the successor to framer-motion)
- **Styling**: `app/globals.css` (theme variables + shared primitives) plus co-located CSS Modules per component/route; `components/charts.module.css` is the one module with several importers, since it styles the chart kit
- **Deployment**: Vercel

## Database Tables

Six tables in Supabase: `category`, `expense`, `budget`, `recurring_expense`, `savings_snapshot`, `tag`.

- `expense.price` is whole kroner, stored as **encrypted decimal text**: `0009_encrypted_fields.sql` widened `expense.price`, `recurring_expense.price`, `budget.budget` and `savings_snapshot.amount` from `bigint` to `text` (and dropped `savings_snapshot`'s `amount >= 0` check, which cannot be expressed about a value the database cannot read — the client enforces it now). `expense.item`, `recurring_expense.item` and `tag.name`/`tag.budget` are encrypted too
- `expense.user_id` scopes data per user via RLS
- **A merkelapp is a row in `tag`** (`0010_tag.sql`): a trip or project with an encrypted `name`, readable `start_date`/`end_date` (both or neither — a check enforces it) and an encrypted `budget`; `expense.tag_id` points at it, `on delete set null`. It replaced the free-text `expense.tag`/`recurring_expense.tag` (dropped in `0011_drop_tag_text.sql`; templates have no merkelapp at all). 0010's backfill made one tag per tagged expense, because ciphertexts of the same name differ and SQL cannot group them; `LedgerProvider` folds same-named tags together once per mount (`planTagMerge`: commonest spelling, widest dates), so names are kept unique in the UI (`/profil/merkelapper` and `createTag` refuse or reuse a duplicate). The provider holds `tag_id` on each expense and resolves `tag` (the name) from `ledger.tags`, so a rename shows everywhere without a refetch. **Per dag** on `/innsikt` is the whole total — tickets bought months ahead included — over the inclusive days from start to end, with the total split into Før/Under/Etter; an undated merkelapp falls back to first–last purchase. Income under a merkelapp is ignored, and tagged spending still counts in the monthly budgets. A new expense whose date falls inside a merkelapp's dates gets it preselected until one is picked by hand
- `budget` entries are per category/month/year, unique on (`user_id`, `category_id`, `year`, `month`) since `0006_budget_owner.sql`, so writes are a single upsert. That migration also replaced three `using (true)` policies (every authenticated user could read and overwrite every other user's budgets) with the owner-scoped `budget_owner`
- Income is identified by `category.kind === "income"`, via the predicates in `lib/categories.ts`; the four kinds are `income`/`fixed`/`variable`/`savings`
- `savings_snapshot` holds one observed balance per (`category`, `date`) — `category` is free text, so a savings category exists exactly when it has a snapshot. It is **fully independent of `expense`**: nothing derives a balance from transactions, which is the point (a fund is worth what the market says, not the sum of deposits into it). Unique on (`user_id`, `category`, `date`), so re-entering a date or re-importing a CSV updates rather than duplicates. This replaced the old `goal` table, dropped in `0005_savings_snapshot.sql`
- `recurring_expense` holds fixed-expense templates (item, price, category, day of month); it carries `user_id` like the others and is fetched by `LedgerProvider` (exposed as `templates`) — `RecurringTemplates.tsx` and `/transaksjoner` read it from there and only write to it directly (insert/update/delete on the template; booking inserts an `expense` with `recurring_id`)

## Key Conventions

- **Amounts and descriptions are end-to-end encrypted in the browser** (`lib/crypto.ts`), under a key the server never sees. Three rules follow and none of them are negotiable without undoing the migration: **nothing may aggregate or filter these columns in SQL** (no `sum(price)`, no `order by price`, no `ilike` on `item`) — every query orders by date/id/category and filters by date/user_id, and all arithmetic happens client-side on decrypted rows; **the ledger is decrypted once, in `LedgerProvider`**, so every consumer downstream (`useMemo`s, search, CSV export, `lib/insights.ts`) sees plain numbers and strings and never touches `lib/crypto.ts` — only the routes with their own one-off reads decrypt themselves (`/budsjett`'s drafts, `/sparing`'s snapshots); and **every write calls `encField` at the call site** on its way to Supabase. The key material (`enc_salt`, `enc_dek`, `enc_dek_recovery`) lives in `auth.users.user_metadata`, the unlocked key in `localStorage` (`budget.dek.v2`) stamped with its user id and a 7-day expiry that slides on every resume, and `EncryptionGate` handles setup, unlock and recovery-phrase recovery. `decField` passes anything without the `gc:` prefix through untouched, so pre-encryption rows keep working until the pass on `/profil` reaches them. See `docs/frontend-architecture.md` -> Encryption
- UI language is Norwegian (bokmål)
- Currency: NOK, formatted as "1 234 kr" via `lib/format.ts`
- No backend API routes — all queries go directly from client to Supabase
- **Category colors come from eight fixed, validated slots** (`--cat-1`..`--cat-8` in `globals.css`), assigned deterministically from the category name hash via `lib/categoryColor.ts`. Use `getCategorySlot` for one category in isolation (pills, dots, single bars) and `categorySlots` wherever several are drawn touching each other (the /sparing stacked chart, where the set-aware version guarantees distinct slots). Then `categoryColor(slot)` for a mark, `categoryTint`/`categoryInk` for the pill. **The slot order is the colorblind-safety mechanism, not a preference** — adjacent slots are what end up touching, and this order is the one that clears the gates; re-ordering or re-picking a step means re-validating the set. This replaced hue-from-hash painted as `hsl(hue, --seg-s, --seg-l)`: HSL lightness is not perceptual, so at a fixed 56% the yellows and cyans measured 1.9:1 against the card (invisible) while the blues sat at 3.5:1, and hues 45° apart came out ΔE 0.2 under deuteranopia — the same color
- Seven routes under `app/(app)/` share one `AuthGate` -> `LedgerProvider` -> `TopNav`/`PeriodPicker` layout: `/oversikt` (dashboard: the income/expense difference, budget gauge and category breakdown), `/transaksjoner` (viewing, adding, editing, deleting transactions, and booking the month's fixed expenses), `/budsjett` (setting budgets), `/innsikt` (the selected period: tiles, a money calendar, a waterfall, a bubble chart), `/trender` (the trailing twelve months: net chart, fixed/variable mix, category trends), `/sparing` (savings balances), and `/profil` (account settings and the Utseende card) with its two settings pages `/profil/kategorier` and `/profil/faste-utgifter`. `/profil` is deliberately **not** a tab — it is reached from the user chip in the header (which is highlighted on all three profile pages), since a profile is not a view of the ledger. Signing out lives there, not in the nav. `TopNav`'s bottom tab bar shows a `short` label per route on phones — six full names do not fit a 375px screen. `/sparing` and the three `/profil` routes are listed in `ROUTES_WITHOUT_PERIOD` in `app/(app)/layout.tsx`, so they render without `PeriodPicker` — savings snapshots sit on arbitrary dates and are shown in full, and settings are not ledger data at all, so a month selection would have nothing to act on
- A new account is seeded with default categories by a trigger on `auth.users` (`0007_seed_default_categories.sql`); without it a signup lands in an app where no form can be submitted, since every entry needs a `category_id`
- The user's name lives in `auth.users.user_metadata.full_name`, not in a table: the session already carries it and `auth.updateUser({ data })` already writes it, so a `profile` table would add a migration, a policy and a fetch to store one string. The avatar follows the same principle: a DiceBear `croodles-neutral` drawing **seeded on the name** (`@dicebear/core` + `@dicebear/styles`), so it exists the moment the account has a name — no storage bucket, no upload, nothing that can 404. It renders as an `<img>` off `toDataUri()`, not as inline SVG: inline would mean `dangerouslySetInnerHTML`, and the seed is user-supplied. The `initials`/`avatarSlot` helpers that drew the old monogram are gone with it
- Changing a password on `/profil` re-authenticates first (`signInWithPassword` with the entered current password) because Supabase's `updateUser` does not check the old one; without it an unlocked laptop is enough to lock the owner out
- Changing an email sends a confirmation to **both** the old and the new address (Supabase's default "Secure email change") and applies only when both are opened; `user.new_email` carries the pending address in the meantime
- Auth is client-only (`@supabase/supabase-js`, implicit flow, no `@supabase/ssr`, no middleware, no route handlers). The four public auth routes sit outside the `(app)` group so `AuthGate` never wraps them. `/nytt-passord` accepts both link shapes — `?token_hash=&type=` via `verifyOtp`, or a session already parsed from the URL fragment by `detectSessionInUrl`
- Migrations in `supabase/migrations/` are applied by hand. An already-applied migration is never edited; a later numbered one supersedes it
- **A date input on iOS Safari is `appearance: none` with `min-width: 0`** (`globals.css`): natively it is a centred button with an intrinsic minimum width wider than half a phone, so it overflowed the two-column entry form. A grid that holds one uses `minmax(0, 1fr)`, not bare `1fr`, whose `auto` minimum lets the cell grow to the input instead
- **The phone's bottom tab bar needs the header without `backdrop-filter`.** `backdrop-filter` makes an element the containing block for its `position: fixed` descendants, so on `.nav` it pinned the "bottom" bar to the header; at ≤640px the header is solid instead, and `.shell` reserves the bar's height at the bottom
- **A tooltip must never overflow the chart it belongs to.** Two rules in `globals.css` box it in: `.card > *` gives every direct child `position: relative; z-index: 1`, so a *later* sibling in the same card (a legend, a stat row) paints over anything overflowing an earlier one — equal z-index, DOM order wins; and `.card` carries `backdrop-filter`, which always makes an element a stacking context, so escaping the card entirely just puts it under the next section. `ChartTooltip` derives its side from the anchor's `y`; a chart whose tooltip would overflow passes `flip` explicitly to point it inward (`ShareBar` does — its bar is 24px from the top of the card, so the derived "below" put the tooltip under the legend; `Sparkline` pins `above` for the same reason, being 32px tall)
- **Every chart is SVG drawn in measured pixels**, from `d3-scale`/`d3-shape` on top of `components/charts.tsx`. Three rules: a chart **measures its own box** (`useMeasure`) rather than stretching a fixed viewBox with `preserveAspectRatio="none"` — that stretch is what forced every old label to be HTML positioned in percentages and every stroke to carry `vector-effect`; **the scale arithmetic lives in `lib/chart.ts`**, not in the component, so it is unit-tested (`lib/chart.test.ts`, `lib/savings.test.ts`) instead of eyeballed; and **there is exactly one tooltip**, `ChartTooltip`, so a hover readout looks and behaves the same on every route. Hit areas are real HTML `<button>`/`<div role="img">` elements tiled over the SVG, not handlers on the shapes, which is what gives keyboard focus, `aria-pressed` and an accessible name carrying the same figures the tooltip shows
- `MonthColumns`' bars are deliberately **not** animated: every month key changes when the window shifts, so the entrance replayed in full on every press of the picker's arrows. Its hover band and tooltip still animate — pointer feedback, not data arriving. The hover band is drawn **only when `onSelect` is given**: it reads as "this column is pickable", so on the read-only charts (`/innsikt`'s net columns, `CategoryDrilldown`) a hover produces the tooltip and nothing else. The selected-month band is unconditional — state, not an affordance
- **Animation is `motion`**, with `<MotionConfig reducedMotion="user">` in `app/(app)/layout.tsx` as the single gate on the OS setting — no component checks the media query itself. Durations and the easing curve come from `lib/motion.ts` (`T_FAST` 140ms for pointer feedback, `T_BASE` 220ms for a state change the user asked for, `T_DRAW` 450ms for data arriving); don't inline a duration. The CSS keyframes that remain (`card-rise` in `globals.css`) are still covered by the blanket `prefers-reduced-motion: reduce` override there. `anime.js` is not installed and should not be: it overlaps `motion` completely
- **The activity table's filters are one row in the table's own grid**, under the column headers, so each control sits above what it narrows: a `DateRangePicker` under Dato, a merkelapp select (in `orderTags` order), a search box under Beskrivelse, min/max side by side under Beløp, a select under Kategori, and a reset ✕ in the actions column. The row is hidden behind a `Filtrer` toggle in the card head, which shows the number of active filters while closed, so a filter left on is never invisible; `/` opens it and focuses the search. On a phone (no headers) the same cells become a two-column form. **A date range replaces the period**: with either end set, the list searches the whole ledger between those dates (an open end runs to the edge of `availableMonths`) and calls `ensureMonthCovered` for both ends, which is what the old `Valgt periode / Alle måneder` scope select did, more precisely. The totals row that sat above the list is gone
- **`Importer CSV` reads a transaction file with a preview and no silent writes** (`lib/importExpenses.ts`, on top of `parseCsv` and `/sparing`'s `parseDateCell`/`parseAmountCell`). It needs a header row naming a date, a description and an amount; category and merkelapp are used when present (an unknown merkelapp is created undated and listed in the preview), and a file exported from this same table reads straight back in. Three rules make it safe to press: the sign in the file is dropped from the amount (`expense.price` is unsigned — the category's kind carries direction) and only used to *guess* the kind of a category the file introduces, and only when the file contains both signs, since an all-positive statement says nothing about direction; rows matching one already in the ledger are counted and skipped, because `expense` cannot carry a unique constraint over columns the database cannot read; and rows whose category is blank are held out of the plan until a fallback category is picked. Everything — the row count, the date range, the duplicates, the categories about to be created and their guessed kinds, and every skipped line with its line number — is on screen before the confirm button writes anything
- Inline spreadsheet-style editing: double-click a row (or press its pencil — a touch screen has no double-click) to edit, new-row input at top of the table on desktop
- **On a phone, `/transaksjoner` is an entry form first.** `.shell` is a flex column at ≤860px and the form card carries `order: -1`, so it sits above the period picker; category is a row of one-tap chips, most-used first; the amount field gets the numeric keypad; inputs are 16px so iOS does not zoom; `Legg til` is a full-width 48px button, and a toast confirms what was added with an `Angre`. List rows are two lines (what and how much, then date · merkelapp · kategori) with edit/delete pinned right
- **Fixed expenses are rows in the transaction list, not a separate panel.** For a single selected month with no filters on, every active template not yet booked that month (`pendingTemplates`, never offered while bookings are unknown — loading, failed or outside the fetched window) shows as a dashed row at the top of the list with ✓ (book it: an `expense` insert with `recurring_id`) and ✕ (not this month: a `missing-fixed` dismissal), plus `Før alle N`. The templates themselves are managed on `/profil/faste-utgifter`, linked from the list's ⋮ menu
- **Secondary card actions live in a `MoreMenu` ("⋮")**, not as a button each in the card head: CSV import and export and the `Endre faste utgifter` link on `/transaksjoner`. `.card > .card-head` has `z-index: 3`, so its popovers hang over the card's later children rather than under them
- `useMemo` is used extensively for derived data (totals, filters, sorts)
- Light/dark theme via `data-theme` on `<html>`; all colors are CSS variables in `globals.css`. **Style and accent** are a second choice: `data-style` (`standard`/`ark`/`glass`/`neu`) and inline `--accent`/`--accent-contrast` on `<html>`, picked on `/profil` and **synced through the account** (`user_metadata.appearance`, applied by `AuthGate` on load and `SIGNED_IN` only; light/dark stays per device). Every other accent token is `color-mix()`ed from `--accent` — never hard-code an accent shade. **Corners are six tokens** (`--radius-card`/`-soft`/`-control`/`-small`/`-chip`/`-bar`), set per style — no literal `border-radius` except `50%` and 1–3px marks, no 999px pills, and chart rects take `barCorner()` rather than an `rx`. Line/area charts take their curve from `useChartCurve()` (straight in Ark). The avatar's background is an accent tint (DiceBear drawn transparent). Glass uses **no `backdrop-filter`** (or masks, fixed backgrounds, SVG filters): it made the app sluggish — translucency only. See `docs/design-system.md`
- One button vocabulary: `.btn` (+ `-primary`/`-ghost`/`-small`/`.is-on`) for text actions, `.icon-btn` (+ `-sm`/`-lg`/`-confirm`/`-dismiss`/`-danger`) for icon-only ones, and an `.icon-btn.is-on` state for a toggle. **Controls come in three heights and nothing else**: 36px (`.btn`, inputs, selects, `.icon-btn-lg`, the user chip), 30px (`.btn-small`, `.icon-btn`, the table's inline cells and filter row), 22px (`.icon-btn-sm`) — set as `height`, not left to padding, which had given a button 33px beside a 41px input. Selects draw their own chevron 12px in from the edge (`appearance: none`). Icons come from `components/icons.tsx` — don't declare a local `IconFoo()`
- Dismissed suggestions are a per-device preference in localStorage (`budget.dismissals.v1`, `lib/dismissals.ts`): per-month "denne faste utgiften gjelder ikke denne måneden" — the ✕ on a fixed-expense row in the transaction list
- The activity table's columns are fixed: date, merkelapp, beskrivelse, beløp, kategori. Column order used to be a per-device preference (drag the headers, arrows in the phone form) and was removed. The /sparing stack order is still one (`budget.savings-order.v1`): drag a legend row by its grip (motion's `Reorder`, so it works on touch — HTML5 drag-and-drop does nothing on iOS), or ↑/↓ on the focused grip. The chart follows the drag live (a `startTransition` preview); the order is stored once, on release. The legend is its own non-scrolling scroll container, because `Reorder` auto-scrolls the nearest scrollable ancestor near the viewport edge and scrolling the page made the drag flicker
- **The period picker's window is 8 months back, the current month, and 3 ahead** — not a trailing 12: a budget is set before its month starts, which is also why the year buttons offer next year. `WINDOW_BEFORE`/`WINDOW_AFTER`/`chartWindow`/`yearAnchor` in `lib/period.ts` own that shape, because `selectYear` needs it too (anchoring a year selection at December would draw April–March). Its arrows move the **selection** as well as the window (`shiftPeriod`), `I dag` selects the current month *and* scrolls back to it (`goToToday`, which is how you get out of a whole-year selection), and multi-select of months is Ctrl/⌘/shift-click. **Year chips combine without a modifier** (`toggleYear`): from a month selection a chip selects that year; while the selection is whole years a chip adds or removes its year (never down to none), so several years work on a phone too, and a chip whose year is partly selected is drawn dashed. **The arrows step by the selection's own span** (`selectionSpan`): a month by a month, a year by a year — one-month steps turned January–December into February–January — and their labels say what they step by (`spanUnit`: måned / år / N år / periode). `periodLabel` names whole years as `2025–2026` or `2023 og 2025`
- **`/innsikt` is the selected period; `/trender` is the trailing twelve months.** `/innsikt` reads `useLedgerSelection` — the month, year or `Alle` the picker holds: four tiles (`Inn`, `Ut`, `Igjen` = income − spending, `Spart` = `Igjen / Inn` as a percentage; savings transfers count as left over, as on `/oversikt`), then `Pengekalenderen` (one month: a Monday-first calendar with each day's top five purchases in the tooltip; several months: a week × weekday heatmap, one block per calendar year, plus the average spend per weekday, the priciest weekday and the days with no spending — counted only over months that have any transaction, since a month with no rows is before the ledger began, not a month of zero spending), `Lønna smelter` and `Bobleregnet`, all computed in `lib/periodStats.ts`, then `Merkelapper` (`TagInsight`, `lib/tags.ts`), which ignores the picker: a trip has its own dates, so it reads the whole ledger and widens the fetch to the first month with data. The three charts share one `categorySlots` map, since they draw every category side by side. Where the inspiration used emoji as category icons, these use the category's colour slot — **no emoji**. `/trender` (net chart, fixed/variable mix, category trends) is over `useAnalysisWindow`. The month-over-month card, the anomaly list, the unregistered-subscription table and the "morsomme tall" were removed, and `MonthOverMonth.tsx`, `Anomalies.tsx`, `lib/subscriptions.ts`, `compareMonths`/`previousPeriod` and `detectAnomalies` went with them
- **`/oversikt` opens with the difference between income and expenses for the selected period** (`Inntekter mot utgifter`) — it answers "am I up or down this month / this year / all time" without reading a chart. It reuses the `summary` totals the gauge already computes, so nothing new is aggregated, and savings sit beside the difference rather than inside it (money set aside is not spent — the same reason the gauge's denominator excludes savings budgets). The period itself is the picker's job: a month, a whole year via the year buttons, or **`Alle`**, which selects every month that has data (`selectMonths` in `lib/usePeriod.ts`, driven by `availableMonths`, which is an all-time list)
- **The rest of `/oversikt` is the gauge and the breakdown, and nothing else.** The collapsible category list it used to carry was a second, read-only copy of `/budsjett`'s rows; the drill-down was only reachable from those rows, so it left with them. Both of the page's sections are conditional, so it also carries an explicit empty state — without one, a month with no budget and no spending renders blank, which reads as a failure
- **`/budsjett` is budgets only; categories are settings.** A row is read-only until its pencil turns the **budget** into an input with a tick/cross; names, kinds, adding and deleting categories live on `/profil/kategorier`, linked from the card head (`Endre kategorier`) and from `/profil`. On a phone the type column is dropped and the row is name + pencil over the three figures. The toolbar's `Lagre N endringer` remains for `Kopier N fra <måned>`, which **fills only the empty budget cells** and never overwrites a value already set (typed or stored) — the button states the count and disappears when there is nothing to copy. A read-only cell shows its *draft* value, marked with `.budget-pending`, so a copied figure is visible before it is saved
- The `/budsjett` columns are `Budsjett` and **`Faktisk`**, and the variance column is oriented so **positive is always the good direction**: `budsjett − faktisk` for spending (what is left), `faktisk − budsjett` for income, because earning more than planned is a surplus, not an overrun
