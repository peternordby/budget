# Frontend Architecture

## Tech Stack

- Next.js 16 App Router (`app/`), React 19, TypeScript
- Supabase client for authentication and data access
- One global stylesheet (`app/globals.css`) plus co-located CSS Modules for component-specific styling — see `docs/design-system.md`
- `d3-scale`/`d3-shape`/`d3-array` (submodules, not the full `d3` bundle) for chart scales and path generation, and `motion` for animation — see Charts below
- `@dicebear/core` + `@dicebear/styles` for the seeded profile avatar — see `components/Avatar.tsx` below

## Route Map

- `app/page.tsx` -> redirects to `/oversikt`.
- `app/visualize/page.tsx` -> redirects to `/oversikt`. Kept only so old links and bookmarks still land somewhere.
- `app/(app)/layout.tsx` -> the layout for all five real routes. Mounts, in order: `AuthGate` (session check) -> `EncryptionGate` (the data key — see Encryption below) -> `LedgerProvider` (the one data fetch, keyed by the signed-in session) -> a `Suspense` boundary wrapping `AppChrome`, which renders `TopNav` + a ledger-error banner + (conditionally) `PeriodPicker` + the page (`children`). `PeriodPicker` is skipped for any route in `ROUTES_WITHOUT_PERIOD` — `/sparing`, whose snapshots sit on arbitrary dates and are shown in full, and `/profil`, which is not a view of the ledger at all. A month selection would have nothing to act on in either, and rendering the picker would imply a filter that does not exist. `AppChrome` is a separate component because it calls `usePathname`, which has to sit inside the `Suspense` boundary alongside the other navigation hooks. The `Suspense` boundary exists because `TopNav` and `PeriodPicker` both call `useSearchParams`, which the App Router requires to sit under a boundary; one boundary here covers both components and every route, so neither page has to add its own.
- `app/(app)/oversikt/page.tsx` -> the dashboard, and now only two things: the budget gauge and the expense breakdown bar. The collapsible category list went, because it was a second read-only copy of `/budsjett`'s rows — and `CategoryDrilldown` went with it, since those rows were the only way to open it here (`/innsikt`'s category tiles still do). `MonthOverMonth` and `Anomalies` moved to `/innsikt`: both compare the selected month with its recent past, which is an insight rather than an overview, and grouping them there puts every "what does this mean" section on one route. Both remaining sections are conditional, so the page carries an explicit empty state — otherwise a month with no budget and no spending renders blank, which reads as a failed fetch rather than an empty month.
- `app/(app)/transaksjoner/page.tsx` -> the ledger: the new-transaction row, `RecurringPanel`, and the activity table (filtering, sorting, inline edit, drag-to-reorder columns, keyboard shortcuts `n` and `/`). A `Søk i hele perioden` toggle swaps the table's source array (and its filter options, empty-state check, and edit-lookup) from the selected months to `ledger.expenses` — the provider's fetched window described below, not all of history, since `ledger.availableMonths` can reach further back; while the toggle is on the UI states the actual month count and range rather than implying completeness. An `Eksporter CSV` button (`lib/csv.ts`) downloads whatever the table currently shows, as raw ISO dates and signed plain integers rather than display-formatted values so a spreadsheet can sort and sum them; being comma-delimited per RFC 4180, Norwegian-locale Excel will prompt for a delimiter on import. `RecurringPanel`'s booked-expenses check deliberately does *not* follow the toggle — it always scopes to the selected month's own expenses, because it answers "has this month's fixed expenses been booked yet", not "what does the table show right now".
- `app/(app)/budsjett/page.tsx` -> the budget editor, split off `/oversikt` so the dashboard keeps the *total* tracker (the gauge) while the *setting* of a budget gets room to be a table. It follows the picker's selected month and refuses to render its rows for a multi-month selection, since a budget belongs to one month and a multi-month write has no meaning. Rows come from `ledger.categories` rather than from the transactions in the period, because a category you have not spent in yet is exactly the one you most need to budget for — which is also why `categorySeries` (`lib/trends.ts`) is not reused here: it seeds from entries. Rows are grouped by kind and then sorted by name, deliberately not by amount: sorting an editing surface by the number being edited makes rows jump while you type. A row is **read-only until its pencil is pressed**, which turns that row's name, kind and budget into controls with a tick and a cross beside them. The tick writes the name and kind as **one** `category` update (both are columns on that table) and the budget separately, with a single refetch across the pair; the cross discards all three. A blanked name is refused with a message rather than silently falling back to the old one, which would look like the save had been ignored. The columns are `Budsjett` and `Faktisk`, and the variance column is oriented so **positive is always the good direction**: `budsjett − faktisk` for spending, `faktisk − budsjett` for income, because earning more than budgeted is a surplus rather than an overrun (the bar's scale and its budget marker key off the plain fact of exceeding the budget, in either direction). The batch write survives for `Kopier N fra <måned>`, which **fills only the empty budget cells** — it used to clear every row the previous month had no budget for, "so the copy is a copy rather than a merge", which made it destructive on the common use: most of the month is budgeted and you want the two rows you forgot. The previous month's budgets are therefore loaded up front rather than on click, so the button can state its count and hide itself when there is nothing to copy; a read-only budget cell renders its *draft*, flagged `.budget-pending`, so a copied figure is visibly not yet saved. Edits collect in a draft map keyed by category id and go out as **one** `upsert` on `Lagre` (the unique index from `0006_budget_owner.sql` is what allows that; the page it replaced did find-then-update-or-insert per category), plus one `delete` for rows cleared back to nothing — a blank field and a `0` mean the same thing, since every reader in the app tests `budget > 0`, and storing a `0` row would claim "budgeted nothing" where the truth is "not budgeted". `Kopier fra <forrige måned>` fills the drafts rather than writing, so it is reviewable and undoable by navigating away; January reads the prior December with the same one-off direct query `/oversikt` used to make, since that month can fall outside the fetched years. The page also owns category CRUD, the only place in the app that has ever had it — delete is disabled while anything references the category, because `expense`, `budget` and `recurring_expense` all point at `category.id` with no cascade and the database would refuse anyway.
- `app/(app)/innsikt/page.tsx` -> where the money goes. It opens with `MonthOverMonth` and `Anomalies`, moved here from `/oversikt`: they are about the selected month against its recent past, so they lead, and every section below them widens to the 24-month analysis window. They keep taking `useLedgerHistory(anchor)` — the trailing **12** months — rather than this page's `months`, since a month-over-month comparison has nothing to do with a two-year trend. Then: an income-vs-expense **net** chart, per-category trend tiles (`lib/trends.ts`, via `Sparkline`), and subscriptions that recur monthly but were never registered as a fixed expense (`lib/subscriptions.ts`). The net chart replaced a fixed-vs-variable split that answered a question nobody was asking; it draws one bar per month from a zero line, and both directions share **one** linear scale (`divergingTicks` in `lib/chart.ts`), so a 1 000 kr deficit bar is a tenth of a 10 000 kr surplus bar and zero lands exactly on a gridline. It reads `aggregateByMonth` directly and renders through the shared `MonthColumns` — the same component `PeriodPicker` and `CategoryDrilldown` use. It used to borrow the picker's column/label/active *treatment* by copying it, on the reasoning that the picker's columns are selection buttons and these are a readout; that difference turned out to be one optional `onSelect` prop, against three separately-drifting copies of an axis, a hover behaviour and a label-thinning rule. A savings-rate section used to sit between the two and was removed outright, taking `savingsRate` out of `lib/trends.ts` with it. The fixed/variable question came back as **"Faste og variable utgifter"**, but asked so that it has an answer: one bar of an average month (committed / discretionary / put aside / never spent), the committed figure as a share of income, the headroom left after it, and an older-half-versus-newer-half comparison of the fixed cost itself. The old stacked column showed the same split every month without saying anything about it; the creep it was supposed to reveal is exactly what a column chart makes you eyeball and miss, so that is now a number with a sparkline under it rather than twenty-four bars. The trend tiles carry a hover tooltip, and it belongs to `Sparkline` now: passing `hover` gives the chart its own pointer tracking and the shared `ChartTooltip`. The page used to own that — a strip of invisible hit areas per tile, one shared hovered index across the grid, and a percentage-positioned tooltip of its own — specifically to keep `Sparkline` presentation-only; the readout ended up being the reason to hover a sparkline at all, so it moved in with the chart. Every statistic on the page is computed over `useAnalysisWindow(anchor, 24)` (the subscription table over its last six months), so the numbers follow the selected period rather than the fetch bounds. "Gjør til fast utgift" reactivates an existing template for the same item when there is one — a *paused* template deliberately keeps its item in the suspect list, so inserting there would create a second template — and stamps the expense rows the detection matched with the template's `recurring_id`, so `RecurringPanel` sees the months already entered by hand as booked instead of offering to generate them again. Clicking a category tile opens `CategoryDrilldown` for that category.
- `app/(app)/sparing/page.tsx` -> savings balances, deliberately **separate from the transaction ledger**: every category merged into one stacked area chart (`StackedAreaChart`) whose legend doubles as the per-category readout and as the control for the stack order, a form to record a value, a CSV importer, and the full snapshot history with per-row delete. There is no separate per-category card: the legend already carries each category's current value, change and staleness, and the chart carries its history, so a second view of the same numbers was removed rather than kept in sync. It reads and writes `savings_snapshot` directly rather than through `LedgerProvider` — nothing else on any route needs the data, and the provider's rolling 24-month window is the wrong shape for a savings history, which is small and only useful in full. There is no edit action: `(user_id, category, date)` is unique and every write is an upsert, so recording the same category and date again corrects the value in place (the card says so), which is also what makes re-importing the same CSV idempotent rather than duplicating.
- `app/(app)/profil/page.tsx` -> account settings, and the one route under `(app)/` that is not a view of the ledger. Four cards: name, email, password, sign out. It reads `supabase.auth.getUser()` rather than taking the session from the layout, because `user.new_email` — the address a change is waiting on — is on the user object and not on `session.user` as the layout passes it around. **There is no `profile` table.** The name is `user_metadata.full_name`, which the session already carries and `auth.updateUser({ data })` already writes; a table would mean a migration, an RLS policy and a fetch for one string. The nav renames itself with no plumbing from this page: `updateUser` emits `USER_UPDATED`, which `AuthGate`'s existing `onAuthStateChange` listener already handles. Two details are load-bearing rather than cautious: the password form **re-authenticates before updating**, since `updateUser({ password })` does not verify the old password and an unlocked laptop would otherwise be enough to change it and lock the owner out; and the email form states that both inboxes must confirm, because Supabase's default secure email change applies nothing until they do, and a field that looks saved while nothing changed is worse than no feedback.
- `app/layout.tsx` -> root layout: font (Schibsted Grotesk) setup, the dark/light theme init script, and the ambient background layer. Applies to every route, including the auth screen.

All six routes under `(app)/` are client components (`"use client"`) and render only after `AuthGate` resolves a session **and** `EncryptionGate` holds the data key, so nothing under `(app)/layout.tsx` runs during static generation.

## LedgerProvider: the single fetch

`components/LedgerProvider.tsx` is the only place that queries `expense`, `category`, `budget`, and `recurring_expense` (exposed as `templates`) for the data all three routes render from. All three routes and `PeriodPicker` read from it via `useLedger()`, `useLedgerHistory()`, `useLedgerSelection()`, and `useAnalysisWindow()` instead of querying Supabase themselves (mutations — insert/update/delete on `expense`, `budget`, and `recurring_expense` — still go straight from the page to Supabase, then push the result back into the provider via `upsertExpense`/`removeExpense`/`refetch`; `RecurringPanel` and `/innsikt`'s "make it a fixed expense" action both write `recurring_expense` this way rather than through a provider mutator, since there is no `upsertTemplate`). A fifth export, `toLedgerEntries(expenses)`, is a plain function rather than a hook — it maps any slice of `ledger.expenses` into the `LedgerEntry` shape `lib/insights.ts` expects, which lets `CategoryDrilldown` and `/innsikt` reshape the provider's whole window instead of being limited to `useLedgerHistory`'s fixed trailing 12 months. The one other legitimate direct `select` is `app/(app)/oversikt/page.tsx`'s previous-period budget lookup: it reads a month that can fall outside the provider's fetched `budget` window (the prior December when editing January), so it stays a one-off query rather than a ledger lookup — the code comments explain why.

- **Window.** The provider fetches a `MonthRef` range (`windowStart`..`windowEnd`), initialized to the trailing 24 months ending on the current month (`WINDOW_MONTHS = 24`). `expense` and `budget` are queried scoped to that range and to `user_id`; `category` is fetched in full; and a separate all-time, date-only query against `expense` populates `availableMonths` (every `YYYY-MM` with at least one transaction) — deliberately unscoped to the window, since `PeriodPicker` needs to offer months older than whatever is currently fetched.
- **`ensureMonthCovered(ref)`** widens `windowStart` backward or `windowEnd` forward to include `ref`, whichever direction is needed (both setters return the same object when no widening is required, so calling it every render settles rather than loops). `PeriodPicker` calls it for every selected month and for **both ends** of its 12-month chart, because the chart's window reaches three months past the anchor and the anchor moves independently of the selection.
- **`useLedgerSelection(selectedKeys)`** filters `ledger.expenses` down to the `YYYY-MM` keys in `selectedKeys` — the exact figures `/oversikt` and `/transaksjoner` scope everything to (`CategoryDrilldown`'s transaction list uses it too, whichever route opened the panel).
- **`useLedgerHistory(anchor)`** returns the trailing 12 months of `ledger.expenses` ending at `anchor`, reshaped into the `LedgerEntry` shape `lib/insights.ts` expects. It has no awareness of the provider's wider window; it slices back to 12 months itself, because `detectAnomalies` treats whatever it's given as the complete history for its averages, and `Anomalies` tells the user it's looking at the last 12 months.
- **`useAnalysisWindow(anchor, length)`** returns the trailing `length` months **ending at the selected month**, clamped at both ends to what has actually been fetched. `/innsikt` and `CategoryDrilldown` bucket every statistic over it (both pass 24). It exists because `windowStart`/`windowEnd` are a fetch detail rather than a user-chosen range: `ensureMonthCovered` widens them in both directions and never narrows them, so deriving the analysis window from them let one click on `PeriodPicker`'s always-present next-year button change every average on two routes, and let the subscription detection examine six months that cannot hold a transaction. **Both clamps are load-bearing.** The end clamp covers the render right after a month outside the window is picked, while `ensureMonthCovered` widens asynchronously (the same transient `bookedKnown`/`covered` handles on `/transaksjoner`). The start clamp stops an anchor deep in the past from reaching back past the fetch, where months that were never queried would render as zeroes indistinguishable from real ones — the same "the window the UI computes over is not the window the data covers" bug the hook exists to fix.
- **The ledger is decrypted here, once.** The five queries return ciphertext; the provider maps every row through `decField`/`decNumber` (`lib/crypto.ts`) before anything reaches state, so every `useMemo`, the search box, the CSV export and all of `lib/insights.ts` see plain numbers and strings and have no idea encryption exists. Two consequences: decrypting is awaited, which reopens the window a superseded fetch could land in — hence the second `active` check after the `Promise.all`s, before any row reaches state; and `load()` is called with a `.catch`, because `decField` throws on a row it cannot open and an unhandled rejection would leave `loading` true forever (a spinner, no banner, indistinguishable from a slow network). This covers the ledger only: the routes with their own direct reads decrypt themselves (`/budsjett`'s draft map, `/sparing`'s snapshots, `/innsikt`'s subscription lookup), and writes are not centralised at all — every route calls `encField` itself on the way to Supabase.
- **`userId`** is exposed so every route's writes and one-off reads filter or set `user_id` from one place rather than re-deriving it from the session.
- **The `error`-vs-empty contract.** `error` is set when the most recent fetch failed and is `null` otherwise; `loading` is a separate flag. On failure the provider sets `error`, sets `loading` false, and returns without touching `expenses`/`categories`/`budgets` — so a failed refetch leaves whatever was previously loaded in place. Only the very first fetch (before anything has ever loaded) can leave them as empty arrays on failure, which is indistinguishable from a month with genuinely no data unless a consumer checks `error` first. `AppLayout`'s `LedgerErrorBanner` surfaces `ledger.error` as a status message above every route for exactly this reason, and `transaksjoner/page.tsx` additionally combines `!ledger.error && covered` (see `bookedKnown` below) before letting `RecurringPanel` treat "nothing booked" as fact.

## `usePeriod` and the URL

The selected period lives in the URL as `?p=<comma-separated YYYY-MM list>&w=<anchor YYYY-MM>` rather than in local state, so every view is linkable, survives a reload, and gives the browser's back/forward buttons their expected meaning.

- `lib/period.ts` is the pure parse/serialize layer: `parsePeriod(p, w, fallback)` and `serializePeriod(state)`. Because the URL is user-editable input, parsing never throws — garbage or missing values fall back to `fallback` (today) for the selection and to the newest selected month for the anchor.
- `lib/usePeriod.ts` wraps that in a hook (`usePeriod(fallback)`) that reads `useSearchParams()` and writes with `router.replace` (never `push` — period changes are view adjustments, and pushing would bury the previous page under history entries). It exposes `selectedKeys`, `selectedList`, `single` (the one selected month, or `null` when zero or many are selected), `anchor`, `ready` (false until the URL carries an explicit selection), and the mutators `selectMonth`, `selectYear`, `shiftPeriod` (moves the selection *and* the window — the arrows used to scroll the chart and leave every figure on the page unchanged, so they looked inert), `goToToday` (selects this month *and* scrolls back to it, which is how you leave a whole-year selection), and `bootstrap`. `bootstrap` is a no-op once `p` is present, so `PeriodPicker`'s "default to the current or most recent month with data" effect can never overwrite a period a user actually linked to.
- All three route pages and `PeriodPicker` call `usePeriod` independently (it derives all state from the URL, not from shared component state), so they always agree on the current period without prop drilling. `/innsikt` calls it to read `selectedKeys` (for highlighting the selected months in its fixed/variable chart) and `anchor` (which it feeds to `useAnalysisWindow` and passes down to `CategoryDrilldown`) — it adds no picker or widening effect of its own; both already live in the shared layout.

## `lib/` — pure modules

- `lib/period.ts` — URL period parsing/serialisation, the period picker's **window shape** (`WINDOW_BEFORE` 8, `WINDOW_AFTER` 3, `chartWindow(anchor)`, `yearAnchor(year)`), plus `periodLabel(selected)` ("mars 2026" / "2026" / "4 måneder 2026" / "7 måneder valgt"). That label was inline in `/oversikt`, with its own hard-coded list of Norwegian month names next to `lib/format.ts`'s; it moved here when `/innsikt` gained the two month-comparison sections, which name the same period.
- `lib/insights.ts` — month-key arithmetic (`monthKey`, `addMonths`, `previousMonth`, `listWindowMonths`), `aggregateByMonth` (buckets a `LedgerEntry[]` into per-month income/expenses/savings/net), `compareMonths` (current vs. previous month, including top category movers), and `detectAnomalies` (large single transactions, category spikes, first-seen categories, same-day/same-item/same-amount duplicates).
- `lib/categories.ts` — the `CategoryKind` type (`income` | `fixed` | `variable` | `savings`) and the `isIncomeKind`/`isSpendingKind`/`isSavingsKind` predicates. This is what replaced the old `category.category === "inntekter"` string check; every kind comparison in the app should go through these predicates, never a category name.
- `lib/period.ts` / `lib/usePeriod.ts` — see above.
- `lib/format.ts` — `formatCurrency`, `formatSignedCurrency`, `formatDate` (parses `YYYY-MM-DD` directly to avoid a UTC-shift bug), `formatDateParts`, `toNumber`, and `MONTH_NAMES`/`monthName`/`monthLabel`. The month names existed as five copies (three `FULL_MONTHS` arrays and two `allMonthOptions` lists) before the budget page would have made it six.
- `lib/autocomplete.ts` — `buildItemIndex` groups a user's past transactions by description into `ItemSuggestion`s (median price, most frequent tag, most recent category); `suggestItems` ranks by prefix match, then substring match.
- `lib/recurring.ts` — pure helpers for fixed monthly expense templates: `materializationDate` (clamps a template's day-of-month to the target month's length) and `pendingTemplates` (which templates haven't been booked yet for a given month; takes a `bookedKnown` flag so a failed or not-yet-fetched read is never mistaken for "nothing pending").
- `lib/trends.ts` — the `/innsikt` calculations: `categorySeries` (zero-filled per-category monthly totals; spending kinds only by default, `includeAllKinds: true` opts every kind in — the flag `CategoryDrilldown` uses since it also opens for income and savings categories), plus `spendingMix`/`mixSummary`. `spendingMix` buckets each month into income, fixed, variable and savings; `mixSummary` reduces that window to the averages the section renders. Three things in it are deliberate rather than incidental: `base` is income *or* the outgoings, whichever is larger, so the bar totals 100 % whether the window overspent or registered no income at all and `leftover` never has to be negative; `fixedShareOfIncome` and `headroom` are `null` rather than `0` when there is no income, because "nothing locked in" and "no income to lock anything against" are different claims; and `trend` needs at least four months and drops the middle month of an odd window, so a single month never leans on one side of the comparison and tilts it. `fixedVariableSplit` and `savingsRate` used to live here — the first was superseded by `spendingMix`, the second removed with its section.
- `lib/dismissals.ts` — the one `localStorage` map (`budget.dismissals.v1`) behind "stop suggesting this", with `useDismissals()`, `parseDismissals` and `missingFixedRef`. Two kinds: `subscription` (keyed by the normalised item name, matching how `detectSubscriptions` groups) and `missing-fixed` (keyed by template id **and** month, because the same template is still expected every other month). It is a preference rather than data — the worst case of it not syncing to the phone is a suggestion reappearing — so it is stored the way the column order and the stack order are, not in a table. The filtering happens at every call site, never inside `lib/recurring.ts` or `lib/subscriptions.ts`: those answer what *is*, this answers what to *nag about*. `Anomalies` reads the same map as `RecurringPanel`, which is what keeps the "N mangler" badge and the missing-fixed anomaly from disagreeing.
- `lib/subscriptions.ts` — `detectSubscriptions`: groups an entry window by normalized item name and flags any group seen in 3 or more of those months at a stable amount (within 15%) that isn't already an active `recurring_expense` template — the "subscriptions nobody registered" list on `/innsikt`.
- `lib/csv.ts` — `escapeCsvField`/`toCsv`: RFC 4180 CSV encoding (CRLF row separators, comma delimiter, quote-doubling) behind the activity table's `Eksporter CSV` button. Plus the reading half, added for the savings importer: `parseCsv` (quoted fields, doubled quotes, embedded delimiters and newlines, CRLF/LF/CR, a leading BOM) and `sniffDelimiter`, which counts `,` `;` and tab outside quoted sections of the first line. The delimiter is sniffed rather than assumed because Norwegian-locale Excel writes `;` — the same locale quirk that makes the export prompt on import.
- `lib/profile.ts` — `fullName` and `displayName` over the session user. `displayName` falls back to the local part of the email rather than the whole address, which truncates to something unrecognisable at nav-chip width. It used to also hold `initials` and `avatarHue`, which existed only to draw the monogram avatar; `components/Avatar.tsx` is a seeded DiceBear drawing now and neither has another caller.
- `lib/chart.ts` — chart arithmetic, deliberately outside the components so it is testable: `axisTicks` (nice gridlines covering 0..max), `shortAmount` ("125k"), `labelledDates` (label thinning by position), `divergingTicks` (one shared step across zero) and `shareWidths` (a hoverable minimum per segment of a 100 %-stacked bar, without the bar overflowing).
- `lib/motion.ts` — one easing curve and three durations (`T_FAST`/`T_BASE`/`T_DRAW`) plus `stagger()`. Everything animated in the app reads its timing from here.
- `lib/categoryColor.ts` — the deterministic name-hash every category-coloured surface uses, now mapping to one of **eight fixed, validated palette slots** rather than to a hue on the wheel. `getCategorySlot(name)` for one category in isolation; `categorySlots(names)` for a set drawn adjacent to each other, which guarantees distinct slots while slots last (each name keeps its preferred slot, walking to the next free one on a collision); `categoryColor(slot)` for a mark, `categoryTint`/`categoryInk` for the activity table's pill. The hue-wheel version failed two measurable checks: at one saturation and lightness for every hue, the yellows and cyans came out at **1.9:1 against the card** while the blues sat at 3.5:1 (HSL lightness is not perceptual), and hues 45° apart — exactly what `categoryHues` produced by spacing a set evenly — came out **ΔE 0.2 under deuteranopia**, the same colour. The slot order is the safety mechanism and is validated as a set in both themes; see `docs/design-system.md` → Category colour for the numbers and the relief rule. It also fixes what `categoryHues` was documented as trading away: adding a category no longer repaints the others unless it actually collides with one.
- `lib/savings.ts` — the `/sparing` calculations. `holdings` groups snapshots per category (newest value, the one before it, the change, and the full history, largest holding first); `totalNow` sums the newest snapshot of every category; `totalSeries` is the load-bearing one — it produces the total at every date any category was observed, **carrying each category's last known value forward** across dates it was not observed. Summing only the rows sharing a date would otherwise draw a total that collapses to whichever single category was updated that day and then jumps back. A category contributes nothing before its first snapshot, since back-filling it would invent history. `parseSnapshotCsv` reads either shape a hand-kept sheet takes — long (`dato;kategori;beløp`) or wide (a date column followed by one column per category), detected from the header — with `parseDateCell` (ISO, plus day-first dotted and slashed forms, rejecting a day the month lacks rather than letting `Date` roll it over) and `parseAmountCell` (spaced/apostrophe/period thousands separators, currency labels, Norwegian decimal comma, parenthesised negatives). A blank cell in the wide shape means "not observed that day" and is skipped rather than recorded as `0`; every rejected row is returned as a message naming its line number, and the page shows all of it in a preview before anything is written, which is what makes guessing the layout and delimiter safe.
  - The stacked-chart half: `stackedSeries(snapshots, order)` returns one `StackBand` per category, bottom-of-stack first, each carrying `values` (`(number | null)[]`), the cumulative `lower`/`upper` edges, and `baselineAt`. **Null means "no observation to claim", which happens only before a category's first snapshot** — after that the last known value carries forward, because a balance persists whether or not you looked at it. Retiring a category is therefore recording a `0`, which carries forward like any other value and contributes no height; no separate "closed" flag exists. `stale` marks a category not observed on the newest date, so the legend can say its band is being carried rather than measured.
  - `baselineAt` is the height of everything *below* a band at every index, including indices where the band itself is absent — which is what `bandShapes` needs. `bandShapes` splits a band into the contiguous runs where it has values and brackets each run with a **zero-height anchor** on that baseline. Without the anchor the stack tears open: the bands above a late-starting category interpolate smoothly from the previous date toward its new height while the category itself begins abruptly at its first date, leaving a wedge of background between two layers that should be flush and misreporting the total across that gap. The anchor claims no balance — zero thickness is exactly what "did not exist yet" should look like — and the band's stroked upper edge deliberately skips anchors, since stroking through one would draw a line down to the baseline that reads as data.
  - `datePositions` places each date as a 0..1 fraction **proportional to elapsed time**, not evenly: snapshots land on whatever dates the user happened to look, and even spacing would draw a two-year gap and a one-week gap the same width. `dayNumber` builds the day count via `Date.UTC` so a date cannot shift across a boundary in a negative-offset timezone (the same trap `formatDate` avoids). `defaultOrder` is largest-holding-first; `reconcileOrder` merges a stored legend order against the categories that currently exist — keeping known names in place, dropping deleted ones, and appending new ones so a fresh import is never invisible.
- `lib/crypto.ts` — the whole encryption scheme; see the Encryption section below.
- `lib/reencrypt.ts` — the one-time pass behind the button on `/profil` that encrypts rows written before encryption existed, plus `countPlaintext` so the button can hide once there is nothing left. Both walk each table a page at a time (`PAGE = 1000`) because PostgREST caps a select at the project's "Max rows": unpaginated, the pass stopped at the first thousand rows per table and `countPlaintext` then reported nothing left to do — the one failure mode here that looks like success. Safe to interrupt and safe to run twice: rows already carrying the `gc:` marker are skipped.
- `lib/supabaseClient.ts` — the Supabase client singleton and `hasSupabaseEnv`.
- `lib/useToast.ts` — `useToast()`, a small hook for a single dismissible/auto-expiring toast (used by `transaksjoner` for undo-delete).

`insights.ts`, `categories.ts`, `period.ts`, `autocomplete.ts`, `recurring.ts`, `trends.ts`, `subscriptions.ts`, `csv.ts`, `savings.ts`, and `categoryColor.ts` each have a co-located `*.test.ts` file exercised by `pnpm test` (vitest). `lib/crypto.test.ts` covers the key material and the field round-trip; `test/integration/` and `test/e2e/` cover the session-scoped key and the sign-out path. Both of those directories are in `vitest.config.mts`'s `include` — they were written before it listed anything but `lib/**`, and silently never ran. `categoryColor.test.ts` covers slot stability, set-wide distinctness and the "adding a category must not repaint the others" property. `chart.test.ts` covers `divergingTicks` and `shareWidths`, and `savings.test.ts` covers the three older helpers (`axisTicks`, `labelledDates`, `shortAmount`) — it has since they lived in `components/StackedAreaChart.tsx`, before the chart kit gave them a home in `lib/chart.ts`; `format.ts`, `supabaseClient.ts`, `usePeriod.ts`, and `useToast.ts` do not currently have tests.

## Charts

Every chart is SVG, drawn in **measured pixels**. `useMeasure` (one `ResizeObserver`) gives the component its box width and it renders at that scale; nothing stretches a fixed viewBox with `preserveAspectRatio="none"` any more. That stretch was the source of most of the awkwardness in the earlier charts: it scales text and strokes non-uniformly — badly on a phone, where the horizontal factor was a third of the vertical — so **every label had to be HTML positioned in percentages over the SVG**, the plot box had to reserve a matching margin as an axis gutter for those labels to line up with SVG coordinates, and every stroke needed `vector-effect: non-scaling-stroke`. Measuring costs a render at width 0 on mount and removes all three.

Three rules hold across the kit:

- **The arithmetic lives in `lib/chart.ts`, not in the components**, so it is unit-tested rather than eyeballed on screen. See the `lib/` section above.
- **There is exactly one tooltip.** `ChartTooltip` takes a pixel anchor, the box width, a title and rows, and decides its own placement (anchored to its own edge within 90px of either end, flipped below the anchor within 78px of the top) — unless the caller passes `flip`, which it must whenever the derived side would take the tooltip outside its chart. Two rules in `globals.css` box it in: **`.card > *` gives every direct child `position: relative; z-index: 1`**, so a later sibling in the same card paints over anything overflowing an earlier one (equal z-index, DOM order wins); and **`.card` carries `backdrop-filter`**, which always makes an element a stacking context, so escaping the card entirely just puts the tooltip under the next section. `ShareBar` hit the first of those: its bar sits 24px from the top of the card, so the derived side was "below" and the tooltip vanished under the legend beneath it. It is `pointer-events: none` — otherwise it steals the pointer from the hit areas underneath and flickers — and `aria-hidden`, because the hit areas already carry the same figures in their accessible names. Its placement transform sits on an outer element and its animation on an inner one, so motion's inline `transform` never competes with the placement.
- **Hit areas are HTML layered over the SVG, not handlers on the shapes.** A tiled row of real `<button>`s when the chart is clickable, `<div role="img">`s when it is a readout. That is what gives keyboard focus, `aria-pressed` and a focus ring without guessing at SVG focus behaviour, and tiling them across the full width means pointing anywhere snaps to the nearest mark.

### The kit — `components/charts.tsx` (+ `charts.module.css`)

`useMeasure`, `ChartTooltip`, `GridLines`, `BulletBar`, `GaugeArc`, `ShareBar`, `Collapse`, `bandLayout`.

- **`GridLines`** puts each value label just above its own gridline at the left edge of the plot, so there is no gutter to reserve and a label cannot drift out of alignment with the line it belongs to.
- **`BulletBar`** is the 6px row strip on `/oversikt` and `/budsjett` — one component, so the two cannot drift apart again. It carries the scaling rule both routes now share: **under budget the track *is* the budget**, so the bar's own length says how much is left; **over budget the track is the spend and the budget is marked inside it**, because otherwise every overspend clamps at a full bar and 101 % and 300 % look identical. It measures itself for a reason — in a stretched viewBox a 3px corner radius on a bar stretched from 100 to 600 units comes out as an 18px skewed cap.
- **`GaugeArc`** is a stroked circle with an animated `strokeDashoffset`, not a `d3-shape` arc: an arc means animating a path string, which motion cannot interpolate, where a dash offset is one number it tweens natively. Its `pace` tick is the fraction of the month elapsed, and it is the whole reason this is a gauge rather than a percentage in a circle — 60 % of the budget spent is fine on the 20th and alarming on the 5th, and the old conic-gradient ring could not say which. Past 100 % the overflow is drawn as a thinner second lap *inside* the ring; overlaying the same colour at reduced opacity was invisible, since the ring underneath is already full and already red.
- **`ShareBar`** is the 100 %-stacked bar on `/oversikt` ("Fordeling") and `/innsikt` ("Faste og variable utgifter"). Those were two near-identical CSS copies, kept separate on the reasoning that they would drift the moment either grew a state — and then both grew the same state, a hover readout. Bar and legend share one lifted `activeKey`, so pointing at either dims the other's non-matching entries. Segment widths come from `shareWidths`, which gives a 0.2 % category a hoverable 3px without the bar overflowing.
- **`Collapse`** animates a card section's height. `/oversikt`'s category list and `RecurringPanel` both used to swap their content in and out with no transition, so the page below jumped by several hundred pixels.

### `components/MonthColumns.tsx`

Months across, kroner up, hover for the figures — in three shapes: a grouped pair (income vs. expenses, in `PeriodPicker`), a single series diverging from zero (net per month, on `/innsikt`), and a single series with a reference marker (spend vs. budget, in `CategoryDrilldown`). Those were three hand-rolled div-and-percentage charts with three hover behaviours and no axis between them; what actually differs is `series` and `onSelect`. Month labels are thinned by available width rather than dropped by index, so two years of months fit a phone-width card.

Three things it does the same way for all three consumers:

- **The bars do not animate.** Every month key changes when the window shifts, so React remounts the marks and a grow-from-the-baseline entrance replayed in full on every press of the picker's arrows — unreadable when stepping through months quickly. The hover band and the tooltip still animate, because those are pointer feedback rather than data arriving.

- **The tooltip is pinned to the top of the plot, at a constant height** (`y: 0`, `flip: "above"`), not to the hovered bar. Riding the bar tops made it jump up and down as the pointer swept across the months, and on the diverging chart it crossed the zero line mid-sweep. A constant height also means it never covers the bar being read.
- **`axisValues={false}`** keeps the gridlines and drops their value labels. `PeriodPicker` uses it: the figures are in the tooltip, and that chart's job is picking a month rather than reading kroner off an axis. The lines stay, because they are what makes two months comparable by eye.

### `components/Sparkline.tsx`

`points: number[]` and `ariaLabel`, plus an optional `hover` (`title(index)`, `value(index)`) that turns on pointer tracking and the shared tooltip. `d3-shape`'s `line`/`area` with `curveMonotoneX`, a gradient fill under the line, and a dot on the last point; the line draws itself in via motion's `pathLength`. It renders a single dot (not a flat line) for a one-point series, sits a flat series on the midline rather than the floor, and insets the plot by 3px top and bottom — the stroke is centred on the path, so plotting the extremes flush against the edge clipped half of it, visible as a flat-topped peak on every tile whose series had a clear maximum.

### `components/StackedAreaChart.tsx`

The `/sparing` chart, plus `StackedAreaLegend` from the same file. Presentation-only: it takes a `StackedChart` from `lib/savings.ts` and a hovered index, and reports hover changes upward. What is load-bearing:

- **The y-scale runs to the topmost gridline, not to the data maximum** (`axisTicks` then `scaleMax`). Scaling to the max put any tick above it at a negative offset, floating its label out of the chart and into the card heading, and left the total line touching the top edge with no headroom.
- `labelledDates` thins the date axis by *position* rather than by every nth date, always keeping the first and last, and dropping anything too close to the last — snapshot dates cluster (several in one month, then a year's silence), so index-based thinning either overlaps or drops the wrong ones.
- Bands are `d3-shape` areas with `curveMonotoneX`. The visible upper **edge** is stroked over the observations only: an anchor point is a drawing device, not a measured value, and stroking through one draws a line down to the baseline that looks like data. A category observed exactly once has no horizontal extent, so it is drawn as a thick tick instead of a zero-width polygon.
- Hovering reports the portfolio, not just one band: the tooltip gives the date, the **sum of every category at that snapshot**, and the change in that sum since the previous snapshot ("Første registrering" at the first).
- The legend is the second readout: it shows each category's value at the hovered date, or its latest value when nothing is hovered, and a change that is `null` (rendered "—") rather than a fabricated figure when either side of the comparison is missing. It owns the reorder controls — drag a row, or use its arrow buttons — and the page persists the result to `budget.savings-order.v1`. The legend lists top-of-stack first so its rows run in the same direction the chart reads from the top down, which means "up" in the legend is *later* in the stack order; the page translates that once.

## Motion

`lib/motion.ts` holds one easing curve and three durations — `T_FAST` (140ms, pointer feedback), `T_BASE` (220ms, a state change the user asked for), `T_DRAW` (450ms, data arriving) — plus a capped `stagger()`. Nothing inlines a duration.

`<MotionConfig reducedMotion="user">` in `app/(app)/layout.tsx` is the single gate on the OS setting for every `motion` animation in the app; the CSS keyframes that remain (`card-rise`) are covered by the blanket `prefers-reduced-motion: reduce` override in `globals.css`. Enter/exit pairs go through `AnimatePresence`: `Toast` and `CategoryDrilldown` were previously unmounted outright, so both animated in and then vanished mid-sentence.

`anime.js` is deliberately not installed. It overlaps `motion` entirely, and two animation engines writing the same element's `transform` is a bug waiting for a busy page.

## `components/Avatar.tsx`

A DiceBear **`croodles-neutral`** drawing, seeded on the display name — the same reasoning as category colours and as the name itself living in `user_metadata`: derived from what the account already has, so there is no storage bucket, no upload and nothing that can 404, and it is stable for as long as the name is. DiceBear also picks the background from a fixed five-colour list off the same seed.

Two implementation notes:

- The `Style` is constructed **once at module scope**. It is a parsed definition rather than per-avatar state, and building it per render would re-parse 24KB of JSON every time the nav re-rendered; the per-name `Avatar` is `useMemo`'d on top of it.
- It renders as an `<img src={toDataUri()}>`, not as inline SVG. Inline would mean pushing the generated markup through `dangerouslySetInnerHTML`, and the seed is a user-supplied string — an `<img>` closes that path entirely, since a data-URI SVG in an `<img>` cannot execute script. (DiceBear does not echo the seed into its output, but the `<img>` means that isn't load-bearing.)

The monogram it replaced took `initials(name)` on `getCategoryHue(name)`; both helpers are gone, since nothing else called them.

## `components/CategoryDrilldown.tsx`

A labelled **non-modal** side panel: `role="dialog"` plus `aria-label`, and deliberately **no** `aria-modal`. There is no focus trap and nothing inerts the page behind it (the CSS has no scrim either, by design), so claiming modality would remove the rest of the page from the accessibility tree while it stayed reachable by Tab. What it does do: move focus to the panel on open, close on Escape or an outside click, and restore focus to whatever triggered it. It shows one category's mean/median per month, a `MonthColumns` chart over `useAnalysisWindow(anchor, 24)` — the trailing 24 months ending at the host route's selected month, clamped to the fetched range, with the heading stating the real month count and bounds rather than a hard-coded "Siste 24 måneder" — a budget-vs-actual table, and the matching transactions for the currently selected period. It takes `category: string | null`, `onClose`, and `anchor` (the host route's own `usePeriod` anchor, threaded in so the panel analyses exactly the months its route does), and is mounted by `app/(app)/innsikt/page.tsx`, opened from a category tile via `setSelectedCategory`. It had a second caller on `/oversikt`, opened from the category rows there; those rows are gone (they duplicated `/budsjett`) and the panel went with them, since nothing else on that page named a category to drill into.

## Auth

Auth is entirely client-side: `@supabase/supabase-js` with no `@supabase/ssr`, no `middleware.ts`, no route handlers, and therefore the **implicit flow** (the JS default), where the session arrives in a URL fragment and `detectSessionInUrl` parses it. There is nothing server-side that could exchange a PKCE code, which is what makes the link handling below the shape it is.

- Four public routes sit as siblings of the `(app)` route group — `app/logg-inn`, `app/registrer`, `app/glemt-passord`, `app/nytt-passord` — so they inherit only the root layout and `AuthGate` never wraps them. `(app)` is a route group and contributes no URL segment, so there is no collision.
- `AuthGate` no longer renders `AuthPanel` inline. With no session it redirects to `/logg-inn` (in an effect, after `loading` resolves — redirecting during render is a state update on another component, and redirecting before `getSession` answers would bounce a signed-in reload to the login screen). `AuthPanel` is now the body of `/logg-inn`, and redirects the other way if a session already exists.
- **`/nytt-passord` is the landing page for both a password reset and an invitation**, which differ only in which email template sent them. It accepts either link shape: `?token_hash=…&type=…` is exchanged with `verifyOtp`, and otherwise it waits for the session `detectSessionInUrl` already parsed from the fragment. Accepting both is what makes it independent of how the Supabase email templates happen to be configured, and the `token_hash` form additionally avoids depending on a fragment surviving `app/page.tsx`'s server redirect.
- **Invitations have no code.** `inviteUserByEmail` is admin-only and needs a service-role key, which must never be shipped to a browser. Invites are sent from the Supabase dashboard; the recipient lands on `/nytt-passord` like any reset.
- Redirect targets use `window.location.origin` rather than an env var, so localhost and budget.nordby.dev both work with no configuration — but both still have to be on the dashboard's redirect allow list.
- A signup would otherwise land in a dead app: nothing in the UI created a category until `/budsjett`, and every form needs a `category_id`. `0007_seed_default_categories.sql` adds a `security definer` trigger on `auth.users` that seeds a starter set. It is `security definer` because the trigger runs before the new user has a session, so `category_owner`'s `user_id = auth.uid()` check would reject the insert.

## Encryption

Amounts and descriptions are encrypted **in the browser**, under a key the server never sees. `select * from expense` in the Supabase dashboard shows `gc:…` where the kroner used to be. `0009_encrypted_fields.sql` widened the money columns from `bigint` to `text` to make room for it.

This is only affordable because nothing server-side ever did arithmetic on the money: every query orders by date/id/category and filters by date/user_id, and all aggregation lives in `lib/insights.ts`, `lib/trends.ts` and friends, on rows already decrypted in memory. **The trade is permanent.** No `sum(price)`, no server-side reports, no sanity-checking a figure in the dashboard. A feature that needs the database to understand the money has to undo the migration, not work around it.

- **The key material lives in `auth.users.user_metadata`**, next to `full_name` — no table, no policy, no fetch. `enc_salt` (random 16 bytes, the PBKDF2 salt), `enc_dek` (the data key wrapped under PBKDF2(password, salt), 300 000 iterations, SHA-256), and `enc_dek_recovery` (the same data key wrapped under the recovery phrase). The salt is random rather than the user id because it must exist before the account does and must survive an email change.
- **The data key is random and wrapped, not derived.** That is the cheaper design, not the fancier one: a password change rewraps 40 bytes instead of re-encrypting the whole ledger.
- **AES-GCM's auth tag is the wrong-password check.** A bad key throws in `decrypt`, so nothing separate has to verify a password.
- **Which columns.** `expense.item/price/tag`, `recurring_expense.item/price/tag`, `budget.budget`, `savings_snapshot.amount`. Dates, category names and kinds, and every foreign key stay in the clear — they are what the queries filter and order on. `savings_snapshot.category` stays readable **deliberately**: it is part of `unique (user_id, category, date)`, and AES-GCM ciphertext differs on every write, so encrypting it would turn each re-imported CSV row into a duplicate instead of an update.
- **Plaintext passes through.** `decField` returns anything without the `gc:` prefix untouched, which is what made the rollout a background pass rather than a flag day: after the `bigint` -> `text` migration the old rows are bare digit strings and keep rendering correctly until the button on `/profil` reaches them. A half-finished pass is a consistent state. `decNumber` additionally swallows failures and returns `0`, so one corrupt row cannot blank the whole ledger — `decField` does not, so a corrupt *description* surfaces as the error banner instead of as silent wrong numbers.
- **The unlocked key lives in `localStorage` with a 7-day sliding expiry**, stamped with its account (`budget.dek.v2`, `"<user id>:<expiry ms>:<base64 key>"`), plus a module-scope copy stamped the same way. The account stamp is checked on both copies, so a second user in the same browser — a shared laptop, or a token refresh that failed without a `SIGNED_OUT` event — gets a password prompt rather than the first user's key decrypting their rows to zeroes. The expiry **slides on every successful resume**, not from first unlock: daily use never asks again, and the machine that stops being used is the machine that locks. Sign-out is the only way to end the window early. A `v1` entry (sessionStorage, no expiry field) is simply not read, so the change costs one password.
  - **This was a deliberate loosening.** `sessionStorage` meant a password on every browser restart *and* every new tab, and the friction was worth trading. What it gave up is bounded and worth stating: a stolen laptop with a live Supabase session now reads the ledger until the window lapses, where before it read ciphertext. The 7 days is what limits that. Unchanged either way: the server never sees the key, and anything running inside the page could always read it.
- **`EncryptionGate` is the one component covering every way an account can arrive**, because they all end in the same two questions — do you have a key, and can you open it. *No key material*: an account older than encryption, or an invited user; set one up and show the phrase once. *Locked*: the ordinary case, password. *Unopenable*: the password was reset by email, which changed the password without touching `enc_dek`, so only the recovery phrase gets back in — and it rewraps `enc_dek` under the current password on the way through.
- **Both flows that wrap the key verify the password first** (`signInWithPassword`), because a typo would wrap the key under a password nobody knows. And a failed metadata save calls `lock()`: `createKeys` unlocks the tab before the wrap is stored, and a key left unlocked but wrapped nowhere would let the user write rows that are unreadable the moment the tab closes.
- **`AuthPanel` unlocks at sign-in**, since the password is in hand exactly there, rather than making `EncryptionGate` ask for the same password one render later. A failure is not reported on that screen — the sign-in did work, and `EncryptionGate` handles every reason the key would not open.
- **Password changes on `/profil` rewrap in the same `updateUser` call** as the password itself. A password that changed without its wrap (or the reverse) locks the owner out of their own figures until they dig out the phrase. The recovery wrap is untouched, so the paper keeps working.
- **The recovery phrase is 120 bits in Crockford-style base32** (no I, L, O or U), so a phrase read off paper cannot be transcribed into a different valid phrase. It is shown exactly once and cannot be recovered — not by us either.

**What this does and does not protect.** It protects against the database and whoever administers it, and — once the 7-day window has lapsed — against a stolen laptop whose browser profile carries a live Supabase session. Inside that window it does not: the key is on disk and the session is live. It does **not** protect against XSS or a malicious extension in the page — anything running in the tab can read `localStorage` and the key in scope — and it cannot protect a user who loses both their password and their phrase. There is no escrow. That is the point.

## The AuthGate blind spot

**A client component rendered inside `AuthGate`'s `children(session)` callback never executes during `pnpm build`.** `next build` only renders what it can reach without a session — the loading and logged-out states — so `LedgerProvider`, all three routes, `PeriodPicker`, `TopNav`, and everything they render are invisible to the build. `pnpm test` doesn't cover this either unless a test explicitly renders that component tree. This project has shipped one temporal-dead-zone `ReferenceError` for exactly this reason: a bug in declaration order inside a component that only runs post-login, caught by neither the build nor the test suite, only by using the app. When touching anything under `AppLayout`'s `children(session)` branch, scrutinize declaration order and actually exercise the page (`pnpm dev`) rather than trusting a green build.
